BSSCI Service Center Functional Documentation

Comprehensive guide for operating sensors, base stations, network topology, telemetry flow, administration and runtime maintenance in one place.

1. Introduction

Service Center is an operational control plane for MIOTY infrastructure: TLS communication, inventory governance, topology visualization and telemetry reliability.

Main objectives

  • Maintain secure transport between base stations and backend services.
  • Manage full sensor lifecycle: create, register, attach, detach, monitor.
  • Provide near real-time observability with dashboard + health pages.
  • Support tenant separation with admin-level global oversight.

Data path

  • Uplinks arrive through TLSServer/BSSCI handlers.
  • Internal queues decouple ingestion from persistence/publication.
  • Data can flow to MQTT and optional storage backends.
  • Frontend reads API projections designed for operational clarity.
Base Station -> TLSServer -> Runtime queues -> MQTT + Timescale/Influx -> UI APIs

2. Quick Start

Minimal commissioning sequence for a clean deployment.

Step 1: Verify containers and services are healthy (`bssci-service-center`, DB, broker, optional Grafana).
Step 2: Open Configuration and validate server/MQTT/storage endpoints.
Step 3: Add base station(s), then define GPS either in edit form or map workflow.
Step 4: Add sensors and run attach flow to selected base station targets.
Step 5: Validate telemetry in MQTT + Logs + System Health.
If sensors are visible but no data arrives, verify attach mapping, registration status and topic path first.

4. Core Workflows

Production-safe way to perform common actions.

Add Base Station

  • Create entry in Base Stations and verify identity fields.
  • Assign GPS to avoid map inconsistencies.
  • Check connectivity and status propagation on Dashboard.

Add Sensor + Attach

  • Create sensor with EUI and optional descriptive label/tag.
  • Use attach action to map sensor to one or more base stations.
  • Confirm sensor row displays attached BS instead of none.

GPS Consistency

  • Use map placement and Save positions.
  • Re-open sensor/base station edit forms and verify same coordinates.
  • Resolve entries listed in Missing GPS assistant.

Incident Triage

  • Start at Dashboard alerts and health indicators.
  • Inspect MQTT publish/reconnect behavior.
  • Correlate queue depth, retry failures and logs.

9. Troubleshooting

Frequent issues and first checks.

Sensor shows BS: none

Re-check attach mapping save response, tenant filters and refreshed sensor state projection.

Map vs device GPS mismatch

Run save/sync cycle and verify no duplicate EUI entry exists in stored map positions.

No sensor traffic in MQTT

Confirm registration + attach state, then inspect MQTT page counters and runtime queue metrics.

Empty analytics panels

Validate datasource, dashboard UID and tenant variable query behavior before UI-level assumptions.

10. Backup/Restore Runbook

Disaster recovery essentials.

Backup scope: DB data + config files + users/tenants + certificates + runtime JSON.
Backup action: run backup script and verify archive completeness.
Restore action: restore data layer first, then runtime files, then restart services.
Validation: login, inventory counts, attach relationships, GPS state, MQTT publish, health metrics.
powershell -ExecutionPolicy Bypass -File scripts\\backup.ps1
powershell -ExecutionPolicy Bypass -File scripts\\restore.ps1 -BackupPath .\\backups\\latest
